# Potential Head-level question: "How would you design a payment API?" #


Say:
"I would first separate the API layer from the business logic and payment processing. The API would validate the request and authenticate/authorize the caller. I would then persist the payment request with an appropriate status such as Pending. For operations that don't need to be synchronous, I would use asynchronous processing through a queue. A worker would process the payment, perform required validations and call downstream systems. I'd make the operation idempotent so retries don't create duplicate payments. I'd also implement structured logging, correlation IDs, monitoring and proper error handling."

Then add:
"For a payment system specifically, idempotency, security, auditability, reliability and reconciliation would be particularly important."



# They may ask: "What is idempotency and why is it important in payments?" #
Your answer:
"Idempotency means that sending the same request multiple times produces the same intended result rather than creating duplicate operations."

Example:
POST /payments

Idempotency-Key: ABC123

If the client sends the request again because of a timeout, the system should recognize ABC123 and return the existing payment result rather than creating another payment.
Then say:
"This is especially important in payments because accidentally processing the same transaction twice can have a direct financial impact."



# "How would you handle failure in a payment system?" #
Say:
"I would distinguish between transient and permanent failures."

Transient:
- network timeout
- temporary downstream failure
- service unavailable
→ retry with exponential backoff.
Permanent:
- invalid beneficiary
- invalid currency
- authorization failure
- compliance rejection
→ don't blindly retry; mark the transaction appropriately and return the failure.
Then mention:
"For asynchronous processing I'd also consider dead-letter queues, monitoring and alerting."
