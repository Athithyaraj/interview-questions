# 1. Middleware
Definition

Middleware is a component in the ASP.NET Core request pipeline that processes HTTP requests and responses.

A request passes through middleware components in sequence.

Client
  ↓
Exception Middleware
  ↓
Logging Middleware
  ↓
Authentication
  ↓
Authorization
  ↓
Routing
  ↓
Controller
  ↓
Response
Example
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();
Custom middleware
public class RequestLoggingMiddleware
{
    private readonly RequestDelegate _next;

    public RequestLoggingMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        Console.WriteLine($"Request: {context.Request.Path}");

        await _next(context);

        Console.WriteLine($"Response: {context.Response.StatusCode}");
    }
}

Register:

app.UseMiddleware<RequestLoggingMiddleware>();
Interview question

Q: What happens if you don't call _next(context)?

The request pipeline stops there, so subsequent middleware/controller may never execute.

# 2. Dependency Injection
Definition

Dependency Injection is a design technique where required dependencies are provided to a class instead of the class creating them itself.

Instead of:

public class PaymentService
{
    private PaymentRepository _repository = new PaymentRepository();
}

Use:

public class PaymentService
{
    private readonly IPaymentRepository _repository;

    public PaymentService(IPaymentRepository repository)
    {
        _repository = repository;
    }
}

Register:

builder.Services.AddScoped<IPaymentRepository, PaymentRepository>();
Three lifetimes
Lifetime	Meaning
Transient	New instance every time
Scoped	One instance per HTTP request
Singleton	One instance for application lifetime
Important interview question

Why is DbContext usually Scoped?

Because DbContext represents a unit of work and is generally intended to be shared within a single HTTP request rather than across requests.

Payment example
Controller
    ↓
IPaymentService
    ↓
PaymentService
    ↓
IPaymentRepository
    ↓
Database

DI allows us to replace implementations easily for testing and maintainability.

# 6. Controllers

Controller handles HTTP requests and returns HTTP responses.

[ApiController]
[Route("api/[controller]")]
public class PaymentsController : ControllerBase
{
    private readonly IPaymentService _service;

    public PaymentsController(IPaymentService service)
    {
        _service = service;
    }

    [HttpGet("{id}")]
    public async Task<IActionResult> Get(int id)
    {
        var payment = await _service.GetPaymentAsync(id);

        if (payment == null)
            return NotFound();

        return Ok(payment);
    }
}
Good architecture

Don't put business logic directly inside controllers.

Bad:

Controller
 ├── Validation
 ├── Business logic
 ├── Database
 └── Response

Better:

Controller
    ↓
Service
    ↓
Repository
    ↓
Database

Controller should primarily handle HTTP concerns.

# 1. OOP — The 4 Main Principles

The four pillars are:

Encapsulation
Abstraction
Inheritance
Polymorphism
1.1 Encapsulation
Definition

Encapsulation means bundling data and the methods that operate on that data together, while controlling access to the internal state.

Example:

public class BankAccount
{
    private decimal balance;

    public void Deposit(decimal amount)
    {
        if (amount > 0)
            balance += amount;
    }

    public decimal GetBalance()
    {
        return balance;
    }
}

Here balance is private.

The outside world cannot directly do:

account.balance = -5000;

Instead, it must use Deposit().

Real-time payment example
Payment
 ├── Amount
 ├── Currency
 ├── Status
 └── ProcessPayment()

The payment object controls how its state changes.

Interview answer

Encapsulation protects an object's internal state by restricting direct access and exposing controlled operations through methods or properties.

1.2 Abstraction
Definition

Abstraction means hiding implementation details and exposing only what is necessary.

Example:

public interface IPaymentProcessor
{
    Task ProcessPaymentAsync(Payment payment);
}

The caller knows:

processor.ProcessPaymentAsync(payment);

but doesn't need to know whether internally it uses:

Stripe
Bank API
AWS
Database
HTTP calls
Real-world example

When you use an ATM, you know:

Withdraw money
Deposit money
Check balance

You don't need to know the internal banking system.

Interview answer

Abstraction focuses on what an object does rather than how it does it.

1.3 Inheritance
Definition

Inheritance allows a class to reuse and extend functionality from another class.

public class Payment
{
    public decimal Amount { get; set; }
}

public class CardPayment : Payment
{
    public string CardNumber { get; set; }
}

CardPayment inherits from Payment.

Payment
   ↑
CardPayment
When to use?

Use inheritance when there is a genuine is-a relationship.

CardPayment IS A Payment
BankTransfer IS A Payment

Don't use inheritance simply to reuse code. Composition is often better.

1.4 Polymorphism
Definition

Polymorphism means the same interface or method can behave differently depending on the object.

Example:

public interface IPaymentProcessor
{
    void Process();
}

public class CardProcessor : IPaymentProcessor
{
    public void Process()
    {
        Console.WriteLine("Processing card payment");
    }
}

public class BankProcessor : IPaymentProcessor
{
    public void Process()
    {
        Console.WriteLine("Processing bank payment");
    }
}

Then:

IPaymentProcessor processor = new CardProcessor();

processor.Process();

The same:

Process()

behaves differently depending on the implementation.

Two types

Compile-time polymorphism

Method overloading:

void Process(int amount)
void Process(decimal amount)

Runtime polymorphism

Method overriding/interfaces:

IPaymentProcessor processor = new CardProcessor();
processor.Process();
# 2. ref vs out vs in

These are parameter modifiers.

	ref	out	in
Input	Yes	No	Yes
Output	Yes	Yes	No
Must initialize before call	Yes	No	Yes
Method can modify	Yes	Yes	No
Purpose	Read/write	Return value	Read-only reference
ref
void Increment(ref int value)
{
    value++;
}

int x = 10;
Increment(ref x);

x becomes 11.

The caller must initialize x.

out
void GetPayment(out decimal amount)
{
    amount = 100;
}

decimal payment;
GetPayment(out payment);

The caller doesn't need to initialize it.

The method must assign the out parameter.

in
void Display(in Payment payment)
{
    Console.WriteLine(payment.Amount);
}

The method receives a readonly reference.

Useful particularly for large value types when you want to avoid copying.

Easy interview answer

ref is read/write, out is output-only, and in is readonly reference input.

# 3. Why is string immutable?

Immutable means once a string object is created, its contents cannot be changed.

string name = "John";

name = "David";

This doesn't modify "John".

A new string object is created/referenced.

Why?

Main reasons:

1. Security

Strings are commonly used for:

URLs
file paths
connection information
tokens

Immutable values are safer to share.

2. Thread safety

Multiple threads can safely read the same string because its contents don't change.

3. String interning

.NET can reuse identical string instances.

string a = "hello";
string b = "hello";

The runtime can reuse the same interned string.

4. Hashing

Strings are commonly used as dictionary keys.

If their content could change after being used as a key, dictionary lookups could break.

If you need many modifications?

Use:

StringBuilder

instead of repeatedly creating strings.

# 4. Nullable Reference Types

Nullable reference types help identify possible null values at compile time.

Without nullable reference types:

string name = null;

With nullable enabled:

string name = "John";

means it shouldn't be null.

string? name = null;

means null is allowed.

Example:

public Customer? GetCustomer(int id)
{
    ...
}

The compiler warns you when you potentially dereference null.

Important

Nullable reference types are primarily a compile-time safety feature. They don't magically prevent null at runtime.

    }

Where used?

Common examples:

Large classes that need separation

# 7. Tight Coupling vs Loose Coupling
Tight coupling
public class PaymentService
{
    private PaymentRepository repository =
        new PaymentRepository();
}

PaymentService directly depends on a concrete implementation.

Changing the repository can require modifying the service.

Loose coupling
public class PaymentService
{
    private readonly IPaymentRepository repository;

    public PaymentService(IPaymentRepository repository)
    {
        this.repository = repository;
    }
}

Now:

PaymentService
      ↓
IPaymentRepository
      ↑
PaymentRepository

The service depends on an abstraction.

Benefits
Easier testing
Easier maintenance
Easier replacement
Better scalability
Follows Dependency Inversion
# 8. How SOLID Improves Testability

Suppose you have:

PaymentService
      ↓
PaymentRepository
      ↓
Database

Testing PaymentService now requires a real database.

With Dependency Inversion:

PaymentService
      ↓
IPaymentRepository

During production:

IPaymentRepository
       ↓
PaymentRepository

During testing:

IPaymentRepository
       ↓
MockPaymentRepository

Example:

var mockRepository = new Mock<IPaymentRepository>();

mockRepository
    .Setup(x => x.GetPaymentAsync(1))
    .ReturnsAsync(payment);

Now you can test business logic without hitting the database.

Interview answer

SOLID improves testability by promoting small, focused classes, abstractions, dependency inversion, and loose coupling, allowing dependencies to be replaced with mocks or stubs.

# 10. List vs HashSet
List

Allows duplicates and maintains order.

var list = new List<int>
{
    1, 2, 2, 3
};
HashSet

Stores unique values.

var set = new HashSet<int>
{

HashSet<T> generally provides O(1) average-time lookup.

List<T>.Contains() is generally O(n).

Interview answer

# 12. IEnumerable vs ICollection vs IList

Think of them as increasing functionality.

IEnumerable<T>
      ↓
ICollection<T>
      ↓
IList<T>
IEnumerable

Primarily allows iteration.

IEnumerable<Payment>

You can:

}

# 13. IEnumerable vs IQueryable

This is very important for EF Core interviews.

IEnumerable

Query operates primarily on objects already available to the application.

IEnumerable<Payment> payments = db.Payments;

Once materialized:

var payments = db.Payments.ToList();

var result = payments
    .Where(x => x.Amount > 1000);

Filtering happens in memory.

IQueryable

Builds an expression tree that a provider such as EF Core can translate to SQL.

var result = db.Payments
    .Where(x => x.Amount > 1000)
    .ToList();

Conceptually SQL becomes:

SELECT *
FROM Payments
WHERE Amount > 1000;
Performance

For database queries, filtering with IQueryable before ToList() generally means less data is transferred from the database.

# 14. IEnumerable vs IAsyncEnumerable
IEnumerable

Synchronous iteration:

foreach (var item in items)
{
}
IAsyncEnumerable

Asynchronous iteration:

await foreach (var item in items)
{
}

Useful when data arrives asynchronously/streaming.

Example:

public async IAsyncEnumerable<Payment> GetPaymentsAsync()
{
    ...
    yield return payment;
}
Interview answer

IEnumerable<T> supports synchronous iteration, while IAsyncEnumerable<T> supports asynchronous iteration and is useful for streaming data without blocking while waiting for each item.

# 18. Covariance and Contravariance

This sounds difficult but the interview explanation can be simple.

Covariance

Allows you to use a more derived type where a base type is expected.

Uses out.

IEnumerable<string> strings = new List<string>();

IEnumerable<object> objects = strings;

Because string derives from object.

Think:

Derived → Base
Contravariance

Allows a base type to be used where a derived type is expected.

Uses in.

Commonly seen with delegates:

Action<object> action = obj => Console.WriteLine(obj);

Action<string> stringAction = action;

Think:

Base → Derived
Easy memory trick
Covariance     → out → produces
Contravariance → in  → consumes
# 19. LINQ — Single vs SingleOrDefault
Single()

Expects exactly one element.

var payment = payments
    .Single(x => x.Id == id);

Throws if:

No element exists
More than one element exists
SingleOrDefault()

Returns default if none exists.

var payment = payments
    .SingleOrDefault(x => x.Id == id);

Throws if multiple elements exist.

Difference
Single
0 → exception
1 → return
2+ → exception

SingleOrDefault
0 → null/default
1 → return
2+ → exception

Use Single when exactly one record must exist.

# 20. Any vs Count

If you only want to know whether something exists:

payments.Any()

is generally preferable to:

payments.Count() > 0

Why?

Any() can stop as soon as it finds one element.

For IQueryable, it can translate to an efficient EXISTS-style database query.

Interview answer

Use Any() when checking existence; use Count() when you actually need the number of elements.

Select

Transforms each item.

var names = customers

Conceptually:

Customer → Name
Customer → Name

Flattens nested collections.

var allOrders = customers
    .SelectMany(x => x.Orders);

Without SelectMany:

Customer
 ├── Order
 ├── Order

Customer
 ├── Order
 └── Order

With SelectMany:

Order
Order
Order
Order
Easy answer

Select transforms; SelectMany transforms and flattens nested collections.

# 22. OrderBy / ThenBy
var result = payments
    .OrderBy(x => x.Currency)
    .ThenByDescending(x => x.Amount);

Meaning:

First sort → Currency
Second sort → Amount descending within each Currency

If you call another OrderBy, you're starting a new primary sort.

OrderBy()
ThenBy()
ThenByDescending()

is the normal pattern for multiple sort levels.

Combines data from two collections based on matching keys.

var result = payments.Join(
    customers,
    p => p.CustomerId,
    c => c.Id,
    (p, c) => new
    {
        Payment = p.Amount,

# 25. ToList vs AsEnumerable
ToList()

Executes/materializes the query and creates a list.

var payments = query.ToList();

After this, you have the results in memory.

AsEnumerable()

Changes the compile-time view to IEnumerable<T>.

var payments = query.AsEnumerable();

With EF Core, subsequent LINQ operations can then be performed client-side, so use this carefully.

Important
db.Payments
    .Where(x => x.Amount > 1000)
    .ToList();

Filtering can be translated to SQL before data is materialized.

Whereas:

db.Payments
    .ToList()
    .Where(x => x.Amount > 1000);

loads everything first and filters in memory.

# 26. ConfigureAwait(false)

ConfigureAwait(false) tells an awaited operation:

Don't need to resume on the original synchronization context.

Example:

await SomeOperationAsync()
    .ConfigureAwait(false);

This has historically been particularly relevant in UI applications and older ASP.NET environments.

Important for modern ASP.NET Core

ASP.NET Core generally doesn't have a custom SynchronizationContext, so ConfigureAwait(false) is usually less important than it was in classic ASP.NET/UI applications.

Interview answer

ConfigureAwait(false) avoids capturing the current synchronization context. In ASP.NET Core, there's usually no SynchronizationContext to return to, so its benefit is generally smaller than in UI or classic ASP.NET applications.

# 30. JWT
What is JWT?

JWT = JSON Web Token.

It's a compact token commonly used to carry claims between parties and for stateless authentication.

Example:

Authorization: Bearer eyJhbGciOi...
# 31. JWT Structure

JWT has three parts:

Header.Payload.Signature

Example:

xxxxx.yyyyy.zzzzz
Header

Contains metadata such as:

{
  "alg": "HS256",
  "typ": "JWT"
}
Payload

Contains claims:

{
  "sub": "123",
  "role": "Admin",
  "exp": 1234567890
}
Signature

Used to verify that the token hasn't been modified.

Important

JWT payload is generally encoded, not encrypted.

Don't put sensitive secrets/passwords into it.

# 56. Transactions

# 57. Concurrency

Concurrency occurs when multiple requests/users access or modify the same data around the same time.

Example:

Request A → Payment balance = 100
Request B → Payment balance = 100

A updates → 50
B updates → 20

Without proper concurrency handling, one update may overwrite another.

# 58. Optimistic Concurrency

Assumes conflicts are relatively rare.

EF Core can use a concurrency token such as:

rowversion

Conceptually:

Read record
   ↓
Version = 5
   ↓
Update WHERE Version = 5
   ↓
If version changed → conflict

Then the application can handle the conflict rather than silently overwriting someone else's changes.

# 59. N+1 Query Problem

Suppose:

var customers = await context.Customers.ToListAsync();

foreach (var customer in customers)
{
    // Load orders
}

You might get:

1 query → Customers

+ N queries → Orders

For 1,000 customers:

1 + 1000 = 1001 queries

That's the N+1 problem.

Solutions include:

Eager loading
Projection
Better query design
Batch queries

Example:

context.Customers
    .Include(x => x.Orders)

Or project only what you need:

context.Customers
    .Select(x => new
    {
        x.Id,
        x.Name,
        Orders = x.Orders.Count()
    });

# 65. Garbage Collection

GC = Garbage Collector.

.NET automatically manages memory for managed objects.

Example:

var payment = new Payment();

When the object is no longer reachable, it eventually becomes eligible for garbage collection.

# 66. How GC Works

Simplified:

Application allocates objects
          ↓
Objects become unreachable
          ↓
GC identifies unreachable objects
          ↓
Memory is reclaimed

.NET uses generations.

Gen 0
 ↓
Gen 1
 ↓
Gen 2
# 67. Gen 0 / Gen 1 / Gen 2
Gen 0

Short-lived objects.

Example:

var temp = new PaymentRequest();

Frequently collected.

Gen 1

Objects that survived Gen 0 collection.

Gen 2

Long-lived objects.

Examples might include long-lived application objects.

Key concept

The GC generally assumes recently allocated objects are more likely to become garbage than long-lived objects.

# 68. Large Object Heap

Large objects are allocated on the Large Object Heap (LOH).

For example, large arrays/buffers.

Large allocations can have different performance characteristics and can contribute to memory pressure.

For high-performance applications, avoid unnecessary large object allocations.

.NET runtime manages the memory.

Memory/resources outside normal GC management.

That's where deterministic cleanup becomes important.

# 70. IDisposable

IDisposable provides a standard way to release resources deterministically.

    }

# 71. using

{
    ...
}

{

Dispose occurs when the block ends.

# 73. Finalizer

A finalizer is used for cleanup of unmanaged resources in certain scenarios.

Syntax:

~MyClass()
{
}

Important

# 79. Why Use Async?

Suppose the API makes a database call:

API Thread
   ↓
Database request
   ↓
WAITING

With synchronous code, the thread can remain blocked waiting for I/O.

With async:

API Thread
   ↓
Start DB I/O
   ↓
Thread returned to pool
   ↓
Database completes
   ↓
Continuation resumes

This can improve scalability for I/O-heavy APIs because threads aren't unnecessarily blocked while waiting.

Important

Async doesn't make the database operation itself magically faster.

It primarily improves resource utilization and scalability during I/O waits.
