## SECTION 1: TECHNICAL ARCHITECTURE & SYSTEM DESIGN

### **Q1: Design a system to handle high-volume payment transactions with guaranteed delivery and eventual consistency. Walk us through your approach.**

**Best Answer:**

Great question. Payment systems require both reliability and scalability—two things that sometimes conflict, so the architecture has to be thoughtful.

Here's how I'd approach it:

**1. Identify Key Requirements:**
- **Guaranteed delivery:** No payments can be lost
- **Eventual consistency:** We can't be transactional across all services, so we embrace eventual consistency
- **High throughput:** Thousands of transactions per second
- **Auditability:** Every transaction must be traceable

**2. Architecture Pattern:**

```
Payment API (Gateway)
    ↓
Message Queue (AWS SQS or RabbitMQ)
    ↓
Payment Processing Service
    ↓
[Success Branch] → Payment DB + Notification Service
[Failure Branch] → Dead Letter Queue + Retry Logic → Manual Review
```

**3. Specific Decisions:**

**API Layer:**
- Lightweight RESTful endpoint that validates the payment request
- Returns immediately (202 Accepted, not 200 OK)—the client knows it's accepted but not processed
- Generates a unique idempotency key (UUID) to handle duplicate submissions

**Message Queue:**
- Use AWS SQS (for cloud-native) or RabbitMQ (for on-premises reliability)
- Why queue first? Decouples the payment request from processing. If processing is slow, API remains responsive
- SQS provides built-in durability, replication, and long retention (up to 14 days)

**Payment Processing Service:**
- Consumes from queue, processes payment (calls bank APIs, updates ledger)
- **Critical:** Implement idempotent processing using the idempotency key
  - Before processing, check if this transaction already exists
  - If yes, return cached result
  - If no, process and store result with the key
- This ensures duplicate messages don't double-charge

**Database Transaction:**
```csharp
// Pseudo-code
var existingPayment = await db.Payments.FirstOrDefault(p => p.IdempotencyKey == key);
if (existingPayment != null) {
    return existingPayment; // Already processed
}

// New transaction
using (var transaction = db.BeginTransaction()) {
    var payment = ProcessPayment(...);
    db.Payments.Add(payment);
    db.SaveChanges();
    transaction.Commit();
}
```

**Failure Handling:**
- If processing fails (bank API down, database timeout), message goes to Dead Letter Queue
- Implement retry logic: exponential backoff (1s → 2s → 4s → 8s → manual review)
- After max retries, send to dead letter queue for human investigation
- Never lose the message—it's in the queue until success or explicit failure handling

**Notification Service:**
- Publish payment completion events (Success/Failure) to event bus
- Notification service subscribes and sends email/SMS/webhooks
- If notification fails, it doesn't block the payment—payment is already complete

**4. Observability & Monitoring:**
- Log every state transition: Request Received → Queued → Processing → Complete/Failed
- Use structured logging (Serilog) with correlation IDs to trace a payment across services
- Monitor queue depth, processing latency, failure rates
- Alert on: Queue growing (processing slower than intake), Dead letter queue filling up, processing time > threshold

**5. Consistency Model:**

```
Strong consistency: API response (immediate)
    ↓
Eventual consistency: Payment actually processed & settled (seconds to minutes)
    ↓
Final consistency: Notifications sent, ledger updated across all services (eventual)
```

This is the pattern used by Stripe, PayPal, Square—because you can't have strong consistency and low latency at scale.

**Why this works:**
- ✅ Guaranteed delivery: Messages stay in queue until processed
- ✅ High throughput: API doesn't wait for processing; queue acts as buffer
- ✅ Resilience: If processor crashes, messages are persisted; another instance picks them up
- ✅ Auditability: Every message, every attempt, every failure is logged
- ✅ Idempotency: Duplicate requests don't cause double-charges

**Tradeoff:** The customer doesn't get instant confirmation—they get "accepted" and eventual notification. This is acceptable because payments inherently take time (bank processing).

```csharp
foreach (var account in accounts) {
    account.Transactions = transactions.Where(t => t.AccountId == account.Id).ToList(); // LINQ to objects
```

```csharp
var data = await db.Accounts
    .Where(a => a.EngagementId == id)
    .Include(a => a.Transactions) // Eager load in single query
    .Select(a => new {
        Account = a,
        Transactions = a.Transactions.Where(t => t.Date >= cutoffDate).ToList() // Filter in DB
```

### **Q3: Describe your approach to handling distributed transaction failures. How do you ensure consistency?**

**Best Answer:**

This is one of the hardest problems in distributed systems, and the key insight is: **you can't have strong consistency at scale, so you design for eventual consistency and handle failures explicitly.**

**The Problem:**

Imagine a payment system where:
- Service A processes the payment
- Service B updates the ledger
- Service C sends a notification

If Service B fails after Service A succeeds, you're in an inconsistent state: payment accepted but ledger not updated.

**Solution Pattern: Saga Pattern (Choreography + Orchestration)**

**Option 1: Event-Driven Choreography (What I've used)**

Each service publishes events; other services react:

```
Payment API
    ↓
Publishes: PaymentInitiated
    ↓
Payment Service
    ↓
Publishes: PaymentProcessed (or PaymentFailed)
    ↓
Ledger Service subscribes, updates ledger
    ↓
Publishes: LedgerUpdated
    ↓
Notification Service subscribes, sends email
```

**Advantage:** Loosely coupled; services don't know about each other  
**Disadvantage:** Hard to track overall transaction state; debugging is complex

**Example from TRI-AUDM:**

```csharp
// Payment Service
public async Task ProcessPayment(PaymentRequest request) {
    var payment = new Payment { Id = Guid.NewGuid(), Amount = request.Amount };
    await db.Payments.AddAsync(payment);
    await db.SaveChangesAsync();
    
    // Publish event—ledger service will react
    await messageBus.PublishAsync(new PaymentProcessed {
        PaymentId = payment.Id,
        Amount = payment.Amount,
        Timestamp = DateTime.UtcNow
    });
}

// Ledger Service (subscribes to PaymentProcessed event)
public async Task Handle(PaymentProcessed @event) {
    try {
        var ledgerEntry = new LedgerEntry {
            PaymentId = @event.PaymentId,
            Amount = @event.Amount,
            Status = "Pending"
        };
        await db.LedgerEntries.AddAsync(ledgerEntry);
        await db.SaveChangesAsync();
        
        // Publish success event
        await messageBus.PublishAsync(new LedgerUpdated { @event.PaymentId });
    }
    catch (Exception ex) {
        logger.LogError(ex, "Ledger update failed for payment {PaymentId}", @event.PaymentId);
        // Publish failure event—triggers compensation logic
        await messageBus.PublishAsync(new LedgerUpdateFailed { @event.PaymentId });
    }
}
```

**Option 2: Orchestration (More explicit)**

Central orchestrator coordinates the saga:

```csharp
public class PaymentSaga {
    private readonly IPaymentService paymentService;
    private readonly ILedgerService ledgerService;
    private readonly INotificationService notificationService;
    
    public async Task Execute(PaymentRequest request) {
        var paymentId = Guid.NewGuid();
        var saga = new SagaLog { Id = paymentId, Status = "Started" };
        await db.SaveAsync(saga);
        
        try {
            // Step 1: Process payment
            await paymentService.ProcessAsync(request);
            saga.Status = "PaymentProcessed";
            await db.SaveAsync(saga);
            
            // Step 2: Update ledger
            await ledgerService.UpdateAsync(paymentId, request.Amount);
            saga.Status = "LedgerUpdated";
            await db.SaveAsync(saga);
            
            // Step 3: Notify
            await notificationService.NotifyAsync(paymentId);
            saga.Status = "Completed";
            await db.SaveAsync(saga);
        }
        catch (LedgerUpdateException ex) {
            logger.LogError("Ledger update failed, rolling back payment");
            
            // Compensation: reverse the payment
            await paymentService.ReverseAsync(paymentId);
            saga.Status = "Rolled Back";
            await db.SaveAsync(saga);
        }
    }
}
```

**Advantage:** Clear transaction flow; easy to debug  
**Disadvantage:** More tightly coupled; orchestrator is a single point of coordination

**How to Handle Failures:**

**1. Idempotency**
Every operation must be idempotent—running it twice = running it once:

```csharp
public async Task ProcessPayment(PaymentRequest request) {
    // Check if already processed
    var existing = await db.Payments.FirstOrDefaultAsync(
        p => p.IdempotencyKey == request.IdempotencyKey);
    
    if (existing != null) {
        return existing; // Already done
    }
    
    // New payment
    var payment = new Payment { IdempotencyKey = request.IdempotencyKey, ... };
    await db.AddAsync(payment);
    await db.SaveChangesAsync();
}
```

**2. Compensating Transactions (Rollback)**
If step 2 fails, undo step 1:

```csharp
try {
    await ledgerService.UpdateAsync(paymentId);
}
catch (Exception ex) {
    logger.LogError("Ledger update failed, compensating...");
    // Reverse the payment
    await paymentService.ReverseAsync(paymentId);
    throw;
}
```

**3. Dead Letter Queues**
If compensation also fails, route to DLQ for manual intervention:

```csharp
try {
    await paymentService.ReverseAsync(paymentId);
}
catch (Exception ex) {
    logger.LogCritical("MANUAL INTERVENTION REQUIRED: " +
        "Payment reversal failed for {PaymentId}", paymentId);
    
    await deadLetterQueue.EnqueueAsync(new ManualReviewItem {
        PaymentId = paymentId,
        Reason = "Reversal failed",
        Details = ex.Message
    });
}
```

**4. Monitoring & Observability**

```csharp
using (var activity = Activity.StartActivity("PaymentSaga")) {
    activity.SetTag("payment.id", paymentId);
    activity.SetTag("payment.amount", amount);
    
    try {
        await Execute();
        activity.SetStatus(ActivityStatusCode.Ok);
    }
    catch (Exception ex) {
        activity.SetStatus(ActivityStatusCode.Error, ex.Message);
        throw;
    }
}
```

**What to log:**
- Every saga step (started, completed, failed)
- Any compensation actions
- Final status
- Correlation IDs to trace across services

**For Corpay's Payments:**

A payment transaction might look like:
1. **Payment Processing Service:** Process payment with bank
2. **Ledger Service:** Record in customer ledger
3. **Settlement Service:** Mark for settlement
4. **Notification Service:** Send confirmation

If settlement fails, compensate: reverse ledger entry, refund to bank, notify customer.

**Key Principle:** Design services expecting they will fail. Build resilience through idempotency, compensation, and observability.

## SECTION 3: AWS & CLOUD-SPECIFIC QUESTIONS

### **Q7: How would you migrate a monolithic application to AWS serverless architecture? What are the challenges?**

**Best Answer:**

I've actually done this—at Novac, we migrated a .NET Learning Management System to a serverless e-learning platform on AWS. Here's the real story, not the theory:

**Phase 1: Assessment (Week 1-2)**

Before moving anything, I analyzed:

1. **What can be serverless?**
   - API endpoints? Yes (Lambda behind API Gateway)
   - Background jobs? Yes (Lambda triggered by SQS/EventBridge)
   - Real-time calculations? Careful (cold start latency matters)

2. **What's the data story?**
   - Relational data? Keep in RDS (SQL Server or migration to PostgreSQL)
   - Unstructured data? S3
   - Session/cache? ElastiCache or DynamoDB
   - Hybrid: SQL Server for relational, DynamoDB for user-specific data

3. **What are the dependencies?**
   - Third-party APIs? (Zoom, payment processors) → Can Lambda call them? Yes
   - File storage? → S3
   - Messaging? → SQS for queuing, SNS for pub-sub

**Phase 2: Strangler Pattern (Gradual Migration)**

Rather than rewrite everything, I used the "strangler" pattern:

**Before:**
```
Client → Monolith (handles API, background jobs, reporting)
```

**After:**
```
Client → API Gateway
            ├→ Lambda (existing endpoints)
            ├→ Lambda (new endpoints)
            └→ Monolith (legacy endpoints still here, gradually replaced)
```

This means:
- New features go to serverless immediately
- Existing features migrate gradually
- Zero downtime
- Easy rollback if needed

**Concrete Example:**

Monolith had a `/api/courses` endpoint. Instead of rewriting, I:

1. **Created new Lambda function**
```csharp
// AWS Lambda handler
public async Task<APIGatewayProxyResponse> GetCourses(APIGatewayProxyRequest request) {
    var courseService = new CourseService(new RDSDatabase());
    var courses = await courseService.GetAllAsync();
    
    return new APIGatewayProxyResponse {
        StatusCode = 200,
        Body = JsonConvert.SerializeObject(courses)
    };
}
```

2. **API Gateway routing**
```
GET /api/courses → Route to Lambda
GET /api/courses/{id} → Route to Lambda
POST /api/courses → Route to Monolith (not migrated yet)
```

3. **Migrated gradually**
   - Week 1: GET endpoints to Lambda
   - Week 2: POST endpoints to Lambda
   - Week 3: All in Lambda, decommission monolith endpoint

**Phase 3: Asynchronous Processing**

Monolith had background jobs (generate reports, process enrollments). In serverless:

**Before (background worker):**
```csharp
while (true) {
    var job = queue.Dequeue();
    ProcessJob(job);
    Thread.Sleep(5000);
}
```

**After (serverless with SQS):**
```csharp
// Lambda function triggered by SQS
[LambdaSerializer(typeof(SimpleSystemTextJsonSerializer))]
public async Task HandleEnrollmentAsync(SQSEvent @event) {
    foreach (var record in @event.Records) {
        var enrollment = JsonConvert.DeserializeObject<Enrollment>(record.Body);
        await ProcessEnrollmentAsync(enrollment);
    }
}
```

SQS automatically triggers Lambda when messages arrive. No polling loop needed.

**Phase 4: Data Migration**

This is the hard part:

1. **Dual writes** (transition period):
   - Monolith writes to both SQL Server AND RDS
   - Lambda reads from RDS
   - Eventually decommission SQL Server

2. **Data validation**:
   ```sql
   SELECT COUNT(*) FROM MonolithDB.Courses
   WHERE Id NOT IN (SELECT Id FROM AWS_RDS.Courses)
   ```
   
   Find any mismatches before fully migrating

3. **Handling large migrations**:
   - Use DMS (Database Migration Service) for initial bulk load
   - Validate data integrity
   - Test recovery procedures

**Challenges I Actually Faced:**

**1. Cold Starts**
- Problem: First Lambda invocation takes 2-3 seconds (initialization)
- Solution: Provisioned Concurrency for critical functions (costs more, but fast)
- For non-critical paths: accepted the cold start

**2. Connection Pooling**
- Problem: Lambda containers are ephemeral; each invocation is a new process
- Monolith used persistent connection pools
- Solution: RDS Proxy handles pooling for us; Lambda just connects

```csharp
// RDS Proxy handles connection pooling
var connectionString = "Server=my-rds-proxy.amazonaws.com;...";
```

**3. Secrets Management**
- Problem: Can't hardcode DB passwords in Lambda
- Solution: AWS Secrets Manager

```csharp
var secretsClient = new AmazonSecretsManagerClient();
var secret = await secretsClient.GetSecretValueAsync(new GetSecretValueRequest {
    SecretId = "prod/rds/password"
});
```

**4. Timeout Handling**
- Problem: Lambda has max 15-minute timeout
- Monolith could run long jobs for hours
- Solution: Lambda triggers Step Functions for long workflows

```
Lambda (5 min) → Step Functions orchestrates → Multiple Lambdas (each < 5 min)
```

**5. Cost Surprises**
- Problem: Didn't account for all the data transfer costs
- Solutions:
  - Keep data in VPC (no data transfer costs)
  - Use S3 Gateway Endpoint (free S3 access)
  - Monitor CloudWatch costs (logging can be expensive)

**Timeline & Effort:**

- Week 1-2: Assessment & planning
- Week 3-4: Build first Lambda functions
- Week 5-8: Strangler pattern gradual migration
- Week 9-10: Data migration validation
- Week 11-12: Decommission monolith, optimize costs

**Total:** ~3 months for a medium-sized system

**Results:**

| Metric | Before | After |
|---|---|---|
| Server cost | $5,000/month (always running) | $800/month (pay per use) |
| Cold starts | N/A | 2-3s on first call |
| Scalability | Manual scaling | Automatic (100s of concurrent invocations) |
| Deployment | 30 min monolith deployment | 2 min per Lambda function |

**Key Lessons for Corpay:**

1. **Use strangler pattern—don't rewrite everything**
2. **Start with stateless APIs—they're easiest to migrate**
3. **Plan for data migration upfront—it's the slowest part**
4. **Test your disaster recovery—Lambda can scale, but can your database?**
5. **Monitor costs—serverless is cheap but can be expensive if misconfigured**

### **Q8: Explain your understanding of AWS Lambda cold starts. When would it matter, and how would you mitigate it?**

**Best Answer:**

Cold starts are one of the most misunderstood aspects of serverless. Let me explain both the problem and when it actually matters.

**What is a Cold Start?**

When Lambda executes a function:

1. **Container initialization** (happens once per container)
   - AWS launches a container
   - Loads runtime (Node.js, Python, Java, C#)
   - Executes `static` initialization code
   - Loads dependencies

2. **Handler execution** (happens every invocation)
   - Your actual code runs

**Cold Start Timeline (C# / .NET):**
- Container initialization: ~1.5-2 seconds (first time)
- Subsequent invocations: ~1-10 milliseconds (reuse same container)

So if you have 10 concurrent users:
- First invocation: 2s latency (cold start)
- Next 100 invocations: ~5ms latency (warm)
- 1 hour later with no traffic: next invocation cold starts again (2s)

**When Cold Starts Matter:**

**High Impact:** (I would optimize)
- Customer-facing APIs where users see the delay directly
- Real-time request-response (payment processing, login)
- APIs with strict SLAs (p99 < 100ms)

**Low Impact:** (I'd accept it)
- Background jobs (async processing, reporting)
- Batch operations
- Non-time-sensitive operations

**When I DON'T worry:**
- Internal APIs (cross-service communication)
- Endpoints that spike periodically (they warm up after first spike)

**Mitigation Strategies (in order of complexity):**

**Strategy 1: Provisioned Concurrency (Simplest)**

```
AWS Lambda Settings:
├─ Reserved Concurrency: 100 (max parallel)
└─ Provisioned Concurrency: 10 (keep 10 warm all the time)
```

This costs ~$0.015/hour per provisioned concurrency, but eliminates cold starts.

**When I'd use it:** Critical customer APIs ($5/month cost is worth zero-latency)

**Example pricing:**
- 10 provisioned instances × 24 hours × 30 days × $0.015/hour = ~$108/month
- But requests are also cheaper under provisioned concurrency

**Strategy 2: Optimize Initialization Code**

```csharp
// SLOW: Database connections in static constructor
public class Handler {
    private static readonly IDatabase db = new Database("connection-string");
    // ↑ This connects to database on every cold start (1-2 seconds)
}

// FAST: Lazy-load database
public class Handler {
    private static Lazy<IDatabase> db = new(() => new Database("connection-string"));
    
    [LambdaSerializer(typeof(SimpleSystemTextJsonSerializer))]
    public async Task HandleAsync(LambdaInput input) {
        var database = db.Value; // Only connects when first needed
    }
}
```

**Strategy 3: Use Lightweight Runtime**

- C# (.NET) cold start: ~2 seconds
- Python cold start: ~500ms
- Node.js cold start: ~300ms

For critical APIs, use Node.js or Python. For business logic, C# is fine.

**Strategy 4: Connection Pooling with RDS Proxy**

```csharp
// WITHOUT RDS Proxy: Each Lambda creates new DB connection (slow)
using var connection = new SqlConnection("Server=mydb.rds...;");
await connection.OpenAsync(); // 100-500ms per invocation!

// WITH RDS Proxy: Reuse existing connections
using var connection = new SqlConnection("Server=my-rds-proxy.rds...;");
await connection.OpenAsync(); // 10-50ms due to connection pooling
```

RDS Proxy costs ~$0.015/hour but saves hundreds of milliseconds on every database call.

**Strategy 5: Request Batching**

Instead of many small Lambda invocations:

```
❌ Bad: 1000 items → 1000 separate Lambda calls → 2000 cold starts (per 10 min)

✅ Good: 1000 items → 1 Lambda call → process in batch → 0 cold starts
```

Process items in batches of 100-1000 rather than one at a time.

**My Personal Approach at XLMS Learning:**

For the e-learning platform, we had different strategies per use case:

1. **Customer-facing APIs** (course list, enrollment)
   - Provisioned Concurrency: 5 instances
   - ~$40/month cost justified by customer experience

2. **Internal APIs** (background processing, reporting)
   - No provisioning
   - Accepted 2-3s cold starts
   - Not visible to users anyway

3. **Batch jobs** (nightly report generation)
   - Scheduled Lambda (no concurrency)
   - Cold starts irrelevant (batch takes minutes anyway)

**Metrics I Monitored:**

```
CloudWatch Metrics:
- Duration (p50, p95, p99) → See cold start impact
- Throttles → If Lambda concurrency maxed out
- Errors → Any timeout failures
- Duration by Initialization Type → Distinguish cold vs warm
```

**What I Logged:**

```csharp
public async Task HandleAsync(LambdaInput input) {
    var context = APIGatewayProxyRequest.LambdaRequestContext; // AWS provides context
    
    logger.LogInformation("InitDuration: {InitDurationMs}ms, Memory: {MemoryMB}MB",
        context.InitDuration, // AWS-provided cold start duration
        context.MemorySizeMB);
}
```

**For Corpay (Payments Platform):**

I'd handle cold starts thoughtfully:

- **Payment API endpoints:** Provisioned Concurrency (user-facing)
- **Settlement processing:** Accept cold starts (background job)
- **Notifications:** RDS Proxy for connection pooling (reduces cold start impact)
- **Real-time dashboards:** Cache frequently used data in ElastiCache

## SECTION 4: PAYMENT-SPECIFIC & DOMAIN QUESTIONS

### **Q9: Walk us through how you would build a payment reconciliation system. What are the edge cases?**

**Best Answer:**

Payment reconciliation is one of the hardest problems in fintech because everything must balance perfectly. If $1 is missing, it's a real $1 that can't be lost.

**The Problem:**

Payment system has multiple sources of truth:
- Our database (what we think happened)
- Bank statement (what actually cleared)
- Third-party payment processor (Stripe, Square, etc.)

If these don't match, something is wrong.

**Core Architecture:**

```
Daily Reconciliation Job (Scheduled Lambda)
    ↓
    ├─ Fetch our records (Ledger Service)
    ├─ Fetch bank statement (Bank API)
    ├─ Fetch processor records (Stripe API)
    ├─ Compare & identify mismatches
    └─ Create discrepancy report for finance team
```

**Implementation:**

**Step 1: Pull Data from All Sources**

```csharp
public class ReconciliationService {
    private readonly ILedgerRepository ledger;
    private readonly IBankApi bankApi;
    private readonly IPaymentProcessor paymentProcessor;
    
    public async Task<ReconciliationReport> ReconcileAsync(DateTime date) {
        var ourRecords = await ledger.GetTransactionsAsync(date);
        var bankRecords = await bankApi.GetStatementAsync(date);
        var processorRecords = await paymentProcessor.GetTransactionsAsync(date);
        
        return Compare(ourRecords, bankRecords, processorRecords);
    }
}
```

**Step 2: Normalize Data**

Bank and processor data come in different formats. Normalize to a common schema:

```csharp
public class NormalizedTransaction {
    public string TransactionId { get; set; }
    public decimal Amount { get; set; }
    public DateTime Date { get; set; }
    public string Status { get; set; } // Pending, Cleared, Failed
    public string Reference { get; set; }
}
```

**Step 3: Three-Way Comparison**

```csharp
public ReconciliationReport Compare(
    List<Transaction> ourRecords,
    List<NormalizedTransaction> bankRecords,
    List<NormalizedTransaction> processorRecords) {
    
    var report = new ReconciliationReport();
    
    // Check 1: Our records vs Bank
    foreach (var ourTx in ourRecords) {
        var bankMatch = bankRecords.FirstOrDefault(b =>
            b.Amount == ourTx.Amount &&
            b.Date == ourTx.Date &&
            b.Reference.Contains(ourTx.ReferenceId));
        
        if (bankMatch == null) {
            report.AddDiscrepancy(DiscrepancyType.InOurRecordsNotInBank, ourTx);
        }
    }
    
    // Check 2: Bank vs Our records
    foreach (var bankTx in bankRecords) {
        var ourMatch = ourRecords.FirstOrDefault(o =>
            o.Amount == bankTx.Amount &&
            // account for 1-2 day delay
            Math.Abs((o.Date - bankTx.Date).TotalDays) <= 2);
        
        if (ourMatch == null) {
            report.AddDiscrepancy(DiscrepancyType.InBankNotInOurRecords, bankTx);
        }
    }
    
    // Check 3: Processor vs Our records
    // Similar logic...
    
    return report;
}
```

**The Tricky Bits (Edge Cases):**

**Edge Case 1: Timing Delays**

Problem: A payment clears on day 1 in our system but day 2 in the bank.

```csharp
// Our record
Payment { Amount: $100, Date: 2024-01-15, Status: "Completed" }

// Bank record
Transaction { Amount: $100, Date: 2024-01-16, Status: "Cleared" }
```

Solution: Use a "window" for matching (1-3 days depending on payment type):

```csharp
var bankMatch = bankRecords.FirstOrDefault(b =>
    b.Amount == ourTx.Amount &&
```

### **Q10: How would you handle idempotency in payment processing? Give a real example.**

**Best Answer:**

Idempotency is THE key pattern in payments. It means: "Calling an operation once is the same as calling it 100 times"—only one payment gets processed.

**The Problem:**

Without idempotency:

```
Client submits payment
    ↓
Network timeout
    ↓
Client didn't get response, submits again
    ↓
Server processes twice—customer charged twice 💥
```

**The Solution: Idempotency Key**

Every payment request includes a unique key (generated by client):

```csharp
[HttpPost("/api/payments")]
public async Task<PaymentResponse> ProcessPaymentAsync(
    [FromBody] PaymentRequest request,
    [FromHeader(Name = "Idempotency-Key")] string idempotencyKey) {
    
    // request.Amount = 100
    // idempotencyKey = "user123-payment-20240115-abc123"
    // ...
}
```

**Step 1: Check if Already Processed**

```csharp
public async Task<PaymentResponse> ProcessPaymentAsync(
    PaymentRequest request,
    string idempotencyKey) {
    
    // Query: Have we seen this key before?
    var existingPayment = await db.Payments
        .FirstOrDefaultAsync(p => p.IdempotencyKey == idempotencyKey);
    
    if (existingPayment != null) {
        // Already processed! Return the original result
        logger.LogInformation("Idempotent retry: returning cached payment {PaymentId}",
            existingPayment.Id);
        
        return new PaymentResponse {
            PaymentId = existingPayment.Id,
            Amount = existingPayment.Amount,
            Status = existingPayment.Status,
            IsRetry = true // Signal to client this is a retry
        };
    }
    
    // New request—process it
    return await ProcessNewPaymentAsync(request, idempotencyKey);
}
```

**Step 2: Process & Store Atomically**

```csharp
private async Task<PaymentResponse> ProcessNewPaymentAsync(
    PaymentRequest request,
    string idempotencyKey) {
    
    var payment = new Payment {
        Id = Guid.NewGuid(),
        IdempotencyKey = idempotencyKey,
        Amount = request.Amount,
        CustomerId = request.CustomerId,
        Status = "Pending",
        CreatedAt = DateTime.UtcNow
    };
    
    using (var transaction = await db.BeginTransactionAsync()) {
        try {
            // Step A: Save payment record with idempotency key
            db.Payments.Add(payment);
            await db.SaveChangesAsync();
            
            // Step B: Process with external service (bank, processor)
            var bankResponse = await bankApi.ChargeAsync(new BankChargeRequest {
                Amount = payment.Amount,
                CustomerId = payment.CustomerId,
                ExternalId = payment.Id.ToString() // Important: link to our ID
            });
            
            // Step C: Update payment status
            payment.BankTransactionId = bankResponse.TransactionId;
            payment.Status = bankResponse.Success ? "Completed" : "Failed";
            payment.ProcessedAt = DateTime.UtcNow;
            
            await db.SaveChangesAsync();
            await transaction.CommitAsync();
            
            logger.LogInformation("Payment processed: {PaymentId}, {Amount}",
                payment.Id, payment.Amount);
            
            return new PaymentResponse {
                PaymentId = payment.Id,
                Amount = payment.Amount,
                Status = payment.Status,
                IsRetry = false
            };
        }
        catch (Exception ex) {
            await transaction.RollbackAsync();
            
            // Mark payment as failed
            payment.Status = "Failed";
            payment.ErrorMessage = ex.Message;
            await db.SaveChangesAsync();
            
            throw;
        }
    }
}
```

**Why This Works:**

1. **First request:** Idempotency key doesn't exist → process payment, store key + result
2. **Retry request (same key):** Key exists → return cached result immediately
3. **Result:** Idempotent—multiple calls = single payment ✅

### **Q14: What's a technical topic you find yourself explaining repeatedly to others? How do you approach it?**

**Best Answer:**

"Async/await. I find myself explaining this constantly because people understand it intellectually but not practically.

Most explanations go: 'Async means non-blocking, uses callbacks under the hood...' which is technically correct but unhelpful.

Here's how I explain it practically:

**The Analogy:**
'Imagine you're at a restaurant. You order food (async call), and instead of standing there blocking the entire counter, you sit down and do other things (other code executes). When the food is ready, they call your name (callback), and you pick it up. Synchronous would be standing at the counter blocking everything until your food is ready.'

**The Code Example:**
```csharp
// Blocking (synchronous)
public void ProcessPayment() {
    var customerData = database.GetCustomer(id);      // Wait 500ms
    var balance = bankApi.CheckBalance(customerId);   // Wait 1s
    var result = processor.Charge(customerId);        // Wait 2s
    // Total: 3.5 seconds before returning
}

// Non-blocking (asynchronous)
public async Task ProcessPaymentAsync() {
    var customerData = database.GetCustomerAsync(id);       // Start, don't wait
    var balance = bankApi.CheckBalanceAsync(customerId);    // Start, don't wait
    var result = processor.ChargeAsync(customerId);         // Start, don't wait
    
    await Task.WhenAll(customerData, balance, result);      // Wait for all to finish
    // Total: 2s (the longest operation) instead of 3.5s
}
```

**The Gotcha:**
I emphasize the most common mistake:
```csharp
// WRONG: Blocking on async (defeats the purpose)
var result = GetDataAsync().Result; // 💥 Deadlock potential

// RIGHT: All the way async
var result = await GetDataAsync();
```

**Why this matters:**
People often think async is about speed, but it's about *concurrency*. If you're calling 100 endpoints, async lets you call all 100 at once instead of one-by-one. That's transformative for API performance.

I find the key is: real code examples over theory, analogies to real-world situations, and always including the gotcha.
